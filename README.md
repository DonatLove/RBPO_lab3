# Лабораторная работа № 4 — вариант 15

REST API «Бюро находок» для Анны Лебедевой. Работа продолжает лабораторную № 3: Spring Boot 3.5, Java 17, PostgreSQL, JPA и транзакционные операции предметной области. В этой версии добавлены HTTP Basic, регистрация, CSRF и разграничение доступа.

## Предметная область

- **Пользователь** подаёт одно или несколько заявлений о пропаже. Учётная запись хранится в той же таблице `users`; имя пользователя уникально.
- **Найденный предмет** имеет состояния `AVAILABLE`, `RESERVED` и `HANDED_OVER`.
- **Заявление** имеет состояния `OPEN`, `MATCHED`, `CLOSED` и `CLOSED_UNMATCHED`.
- **Претензия** связывает заявление с найденным предметом; состояния: `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED`, `HANDED_OVER`.
- **Акт передачи** связан с претензией; на одну претензию допускается не более одного акта.

В PostgreSQL используются внешние ключи, уникальные ограничения, проверки непустых значений и допустимых состояний. Приложение подключается под отдельной ролью `lost_found_app` с правами только на таблицы и последовательности схемы. Изменение категории предмета или заявления запрещено, если уже есть связанные претензии: это сохраняет их согласованность.

## Бизнес-операции

Все операции доступны под `/api/business` и выполняются в транзакциях с блокировками строк:

1. `POST /claims/{id}/approve` — одобрить ожидающую претензию; резервирует предмет и сопоставляет заявление.
2. `POST /claims/{id}/reject` — отклонить ожидающую претензию.
3. `POST /claims/{id}/cancel` — отменить ожидающую или одобренную претензию; при отмене одобренной записи освободить предмет и открыть заявление.
4. `POST /claims/{id}/handover` — зафиксировать передачу по одобренной претензии; создаёт акт и закрывает связанные записи.
5. `POST /loss-reports/{id}/close-without-match` — закрыть открытое заявление без совпадения и отклонить связанные ожидающие претензии.

Операции проверяют текущее состояние всех затронутых сущностей. CRUD-эндпоинты не позволяют напрямую менять состояния: переходы выполняются бизнес-операциями.

## Аутентификация и доступ

Используется **HTTP Basic**. Пароли регистрируемых пользователей проверяются на длину от 12 символов, заглавную и строчную буквы, цифру и специальный символ; хранятся только в виде BCrypt-хеша. Публичная регистрация всегда назначает роль `USER`. Административную роль нельзя запросить в теле регистрации.

| Возможность | USER | ADMIN |
|---|---:|---:|
| Просмотр найденных предметов | Да | Да |
| Создание и изменение найденных предметов | Нет | Да |
| Создание и изменение собственных заявлений; чтение, создание и отмена своих ожидающих претензий | Да | Да |
| Просмотр всех заявлений и претензий | Нет | Да |
| Отмена собственной ожидающей претензии | Да | Да |
| Одобрение, отклонение, передача, закрытие заявления | Нет | Да |
| CRUD пользователей и актов передачи | Нет | Да |

Пользователь может читать и менять только свои заявления; для собственных претензий ему доступны чтение, создание, удаление ожидающей записи и её отмена. Состояние учётной записи хранится в полях `enabled` и `locked`; отключённые и заблокированные записи не проходят аутентификацию. Самостоятельная регистрация не выдаёт повышенных прав.

Изменяющие запросы защищены CSRF. Получите токен запросом `GET /api/auth/csrf`, сохраните cookie сессии, затем отправляйте значение `token` в заголовке, указанном в поле `headerName` (обычно `X-CSRF-TOKEN`). Запросы чтения токена и регистрации доступны без Basic-аутентификации; регистрация также требует CSRF-токен.

Ошибки возвращаются без stack trace и секретов: `401` — нет или неверны учётные данные, `403` — недостаточно прав или недействителен CSRF-токен, `400` — ошибка входных данных или бизнес-правила, `404` — сущность не найдена, `409` — дублирующая запись или конфликт БД.

## Подготовка PostgreSQL

Для чистой базы данных выполните:

1. Создайте базу `lost_and_found`.
2. Подключитесь к служебной базе `postgres` под администратором и выполните `sql/03-create-app-role.sql`, заменив пароль-заглушку.
3. В базе `lost_and_found` выполните `sql/01-schema.sql`, затем `sql/04-grant-app-permissions.sql`, затем `sql/02-sample-data.sql`.

В демонстрационных данных есть учётные записи `admin` / `AdminDemo#2026` (роль ADMIN) и `sample.user` / `UserDemo#2026` (роль USER). Они предназначены только для локальной учебной базы. Не используйте эти пароли в общедоступной среде.

Если база уже создана для лабораторной № 3, не запускайте повторно скрипт с исходными тестовыми записями `02-sample-data.sql`. Выполните `sql/05-upgrade-users-for-security.sql`, затем `sql/06-upsert-security-demo-accounts.sql` и повторно `sql/04-grant-app-permissions.sql`. Старые строки пользователей будут отключены; существующие заявления и связи сохранятся.

## Запуск приложения

Нужны JDK 17 или новее и Maven. Укажите параметры соединения (для PowerShell):

```powershell
$env:DB_URL = "jdbc:postgresql://localhost:5432/lost_and_found"
$env:DB_USERNAME = "lost_found_app"
$env:DB_PASSWORD = "ПАРОЛЬ_РОЛИ_БД"
mvn test
mvn package
mvn spring-boot:run
```

Hibernate проверяет готовую схему (`ddl-auto: validate`) и не меняет её автоматически. SQL-скрипты нужно выполнить перед запуском. Не сохраняйте реальные пароли в Git или в архиве проекта.

## REST API и Postman

CRUD-ресурсы: `/api/users`, `/api/found-items`, `/api/loss-reports`, `/api/item-claims`, `/api/handover-records`. Создание заявления связывает его с аутентифицированным пользователем; `applicantId` из запроса не принимается.

В `postman` находятся коллекция, окружение и OpenAPI-описание. Импортируйте `Lost and Found API.postman_collection.json` и `Local.postman_environment.json`, затем выберите окружение **Lost and Found - Local**. Для сквозного сценария используются демонстрационные учётные записи из SQL. Убедитесь, что Postman сохраняет cookie сессии между запросами, и выполняйте запросы папки **End-to-end scenario** по порядку. Она проверяет отказ USER при одобрении, одобрение и передачу от ADMIN, обе отмены, отклонение претензии и закрытие заявления без совпадения.

Папка **Authentication & access** отдельно проверяет выдачу CSRF-токена, регистрацию без привилегий и ответы с ограниченным доступом. Для повторной регистрации задайте новое уникальное значение `registrationUsername` в окружении.

## Проверки

`mvn test` использует H2 в режиме PostgreSQL и проверяет регистрацию и BCrypt, CSRF, роли, ограничения владельца, статусы учётной записи, согласованность бизнес-операций и защиту связанных категорий. Для проверки подключения и схемы PostgreSQL запускайте приложение с переменными окружения из раздела выше.
